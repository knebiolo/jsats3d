## 4. WHAT CHANGED FROM 2019 — READ BEFORE TOUCHING ANY ALGORITHM

### 4.1 Hardware
The 2025 array is a **mixed deployment** of two ATS Trident receiver models:

- **SR3017** — shore-based, externally powered, **GPS clock sync via external
  antenna**, CSV output to removable SDHC.
- **SR3001** — autonomous node, battery powered, **no GPS**, internal clock
  only, logs decode time + tag code to SD media, optional pressure/temperature/
  tilt sensors.

Mixed array means: ingestion must be `receiver_type`-aware, and the clock
synchronization path differs by receiver class. Do not write a single
one-size-fits-all ingest parser or sync routine.

### 4.2 The multipath problem
The 2019 multipath rejection was a **supervised machine-learning classifier**
(SVC / Naive Bayes / CART / KNN; KNN performed best) trained on per-detection
signal quality features: **SNR, NBW, FreqOff, Amplitude**.

The ATS output does not provide that full feature set. **Amplitude is available
(in dB).** The rest must be treated as unavailable until the schema audit
(Section 5, Gate 0) proves otherwise.

Therefore: **M4 in the legacy plan is not a patch. It is a new algorithm.**
Treat multipath rejection as a first-class design problem, not an adapter
concern.

### 4.3 Architectural consequence
The legacy constraint "preserve `jsats3d.py` contracts, ingest via a
compatibility adapter" is **relaxed for this project**. The target architecture is:

- A `receiver_type`-aware ingestion layer (per-model parsers).
- A **pluggable multipath filter interface**, so the 2019 supervised classifier
  and the new 2025 filter are swappable implementations behind one contract.
- A **receiver-class-aware synchronization layer**.
- The Deng TDOA positioning solver and the kernel density code are reused
  as-is wherever possible — the math did not change, the inputs did.

Preserve legacy math. Do not preserve legacy schema assumptions that encode
sensor fields the new hardware does not produce.

## 7. MULTIPATH REJECTION — DESIGN SPECIFICATION

### 7.1 Approach
**DBSCAN, unsupervised, per tag per receiver.** There is prior DBSCAN
experimentation in the repository (`notebooks/dbscan_multipath.ipynb` and the
associated checkpoint). **Read that notebook before writing new code.** Report
what was tried, what worked, and what the prior conclusions were. Reuse and
extend it; do not reinvent it.

### 7.2 Feature set (approved)
Computed per tag × receiver:

1. **Lag from first arrival within the PRI epoch** — the primary physical
   discriminant. A direct-path arrival is the first arrival; reflections arrive
   later by the extra path length divided by the speed of sound.
2. **Amplitude relative to the epoch maximum** — reflections lose energy at the
   reflecting surface and over the longer path. Relative, not absolute, so it
   is robust to per-unit gain differences.
3. **Epoch rank** — ordinal position of the detection within its epoch.
4. **Inter-detection interval** — spacing to neighboring detections of the same
   tag at the same receiver.

If Gate 0 reveals a noise-level or frequency-offset field, propose adding them
and justify the addition against a validation metric before adopting.

### 7.3 Amplitude normalization
**Assume amplitude is NOT comparable across receivers until proven otherwise.**
Implement a per-receiver amplitude normalizer as a required, explicit step.
Preferred formulation: express amplitude relative to the epoch maximum for that
tag at that receiver, which is self-normalizing. If an absolute normalization is
also needed, base it on the deployed gain/threshold settings once obtained, and
document the transform. Do not normalize using a statistic derived from the
study detections themselves without flagging the circularity.

### 7.4 Clustering parameters
**Use a fixed, physically derived `eps`, documented in code comments and in the
journal. Do not auto-tune `eps` per group.**

Rationale to state to the junior dev: auto-selecting `eps` per tag-receiver
group (k-distance elbow or similar) silently changes the rejection regime
between groups. Two fish processed the same day would be filtered by different
criteria, and nothing in the output would reveal it. That is unreviewable and
indefensible under peer review.

Derive `eps` from acoustics: the maximum plausible reflection path delay given
the array geometry, the water depth, and the distance to reflecting surfaces,
divided by the speed of sound. Compute it, write down the derivation, and hold
it fixed. If a different value is needed, change it deliberately, once, for the
whole study, with the change recorded.

`min_samples` likewise fixed and justified.

### 7.5 Known limitation to carry forward
Close proximity detection interference (CPDI) was not solved by any 2019
classifier and will not be solved by this one. It is a deployment geometry
problem — receivers too near reflective surfaces. Identify and report CPDI-
affected receivers; do not attempt to filter your way out of it.

## 9. CLOCK SYNCHRONIZATION — TRUST BUT VERIFY

**The field crew reports that receiver clocks are synchronized. This has not
been verified and is not to be assumed.** The SR3017 units have GPS clock sync;
the SR3001 autonomous nodes do not. In 2019 a residual-based check of this
exact kind is what revealed the clocks were in fact not synchronized.

### 9.1 Mandatory verification gate
Before any positioning solver is run, and regardless of what the metadata or
the field crew claims:

1. Enumerate beacon epochs.
2. Compute time-of-arrival residuals against known or solvable receiver geometry.
3. Report, **per receiver**: clock offset, drift rate, residual distribution,
   and the time span over which drift was estimated.
4. Produce a residual plot per receiver as a reviewable artifact.

Run this on **every receiver, including the GPS-synced SR3017 units.** A GPS
antenna that was disconnected, obstructed, or misconfigured produces a unit that
reports itself as synchronized and is not.

### 9.2 Error budget
**1 ms of timing error ≈ 1 m of position error.** State this in every discussion
of timing with the junior dev.

- Target working resolution: **6 decimal places (microsecond)**, which was
  sufficient in 2019. Sub-microsecond precision is not required.
- **Residuals exceeding 0.5 ms: emit a prominent flagged warning and continue.**
  Do not halt. Do not silently proceed either — the warning must appear in the
  run log, in the gate report, and in the journal entry.
- Receivers with persistent out-of-budget residuals are flagged in the output
  database so that downstream positions computed from them are traceable.

## 10. TEMPERATURE & SPEED OF SOUND

Speed of sound in water is over 1 km/s at 20 °C and is **highly sensitive to
temperature**. Small temperature errors produce large ranging errors. Treat the
sound speed model as a first-order accuracy driver, not a detail.

- A **temperature string** is deployed again for 2025. This is the authoritative
  temperature source.
- **Do not use the on-receiver temperature sensors for sound speed.** In 2019
  they were evaluated and found insufficiently precise. They may be retained for
  diagnostics only, clearly labeled as such.
- Baseline: a mean temperature series interpolated to detection timestamps,
  matching the 2019 approach.
- **Permitted experiment:** evaluate whether a depth-resolved profile from the
  string (rather than a single mean) measurably improves positioning residuals.
  If stratification is present, it may. Treat this as a hypothesis to test
  against Gate 4 metrics, not as a default. Report the comparison; adopt only if
  it demonstrably improves RMSE on the stationary holds.
- Sound speed formulation and its temperature dependence must be stated
  explicitly in code and documentation, with the source cited.

## 11. ACCEPTANCE CRITERIA

### 11.0 Published parity — the non-negotiable standard
The software may change substantially. It may stop being `jsats3d` in any
meaningful sense. That is acceptable. **What is not negotiable is parity with
the published 2021 result.** Nebiolo & Meyer (2021), *Animal Biotelemetry* 9:20,
is the scientific record this work must stand alongside.

Published 2021 performance, to be matched or exceeded:

| Metric | 2021 published result |
|---|---|
| Accuracy — metronome receiver RMSE vs. surveyed position | X 0.02 m, Y 0.05 m, Z 0.004 m |
| Precision inside convex hull (σ) | X 0.06 m, Y 0.06 m, Z 0.12 m |
| Precision outside convex hull (σ) | X 0.25 m, Y 0.33 m, Z 0.27 m |

Published methodological commitments that must be preserved regardless of
implementation changes:
- Positions from inside the convex hull are the reportable product. Positions
  outside the hull are extrapolation and must be labeled as such.
- Accuracy is assessed by comparing an epoch-by-epoch position determination of a
  receiver at a known surveyed position against that surveyed position, via RMSE.
- Precision is described by the standard deviation of the least-squares solution.
- Solutions are retained even when physically impossible (e.g. above the water
  surface, on dry land); they serve as presence data and retaining them costs
  nothing. Do not silently discard them.
- CPDI is a known unresolved limitation. Report it; do not claim to have solved it.

If any change to the pipeline degrades a published metric, that is a blocking
defect, not a tradeoff — unless the owner explicitly accepts it and the
justification is recorded in `LONG_TERM_CONTEXT.md`.

### 11.1 2025 acceptance
The 2025 pipeline must perform **as well as or better than the 2019 study.**

1. **< 1 m precision for positions inside the convex hull** of the receiver
   array. Positions outside the hull are extrapolation and are to be flagged as
   such, not reported as equivalent-quality data.
2. **Publish RMSE for stationary hold tests.** Compute and report, do not merely
   check a threshold.
3. **Visual comparison of solved tracks against tag drag efforts.** Produce
   overlay plots of computed trajectory vs. the reference drag track.
4. Report positional yield: detections in, positions out, and the rejection
   accounting at each stage.

### 11.2 Upstream data provenance — resolve before M1
The detection data is delivered by a third party (Spheros) as a concatenated CSV
per study year. Two provenance issues must be settled with the owner before
ingestion work begins:

1. **Upstream multipath removal.** Preliminary cleaning by the data provider is
   expected to include multipath removal. Building a filter on top of an
   uncharacterized upstream filter makes the lag distribution truncated in an
   unknown way and the rejection accounting uninterpretable. **Obtain raw,
   unfiltered detections in addition to the cleaned delivery, plus written
   documentation of the upstream method.** Do not proceed with M4 design against
   pre-filtered data alone.
2. **Dropped fields.** Confirm whether background noise level and transmitter
   frequency exist in the receiver output upstream and are being discarded during
   concatenation. If recoverable, they should be recovered — they are the closest
   available analogues to the 2019 feature set.

A milestone is not complete because the code runs. It is complete when the
artifact demonstrates the criterion.
