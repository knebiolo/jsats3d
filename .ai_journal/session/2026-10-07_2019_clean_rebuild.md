## Findings and lessons
- The sync window explains the extra raw rows but not the deep Z mismatch. The reference deep values are rounded (246.5, 246.42, 250.63) while ours are 3-decimal medians, which points to a manual override in the legacy workflow (unconfirmed). This is also why the earlier "verified" R03 coordinates (20.1/-3.76/250.63) are simply the reference values.
- The first rebuild finds more solutions per tag but fewer tags with solutions (128 vs 146) than the reference; the two counts are not directly comparable (older version, no `solNo`). Accuracy against truth for 2019 is not computed.
- Operational: never query a DB during a run (lock crash at E1F8); `Tee-Object` on a native command buffered all output in the first import and looked like a hang (use direct runs or file redirection); `process()` wipes `positions` at the start of the tag loop (`fresh_folder`), so a resume must not call it; a bulk delete on a 10 GB DB needs a `VACUUM`; K: network reads of big `.DET` files can fail with PermissionError, so work from a local copy.
- Alignment with the project lead's priorities: clock sync is the most important step, then receiver positions and multipath; the plan is to verify on the static beacon tags first, then on ENT-01/ENT-05, and to look for intermediate clock jumps and for how to tell which detections are multipath (most are), before trusting positions.
