### 2025 step 5 transNo loss investigated (appended 2026-10-01 22:05 local PDT)
- Mechanism: `multipath_data_object` (`jsats3d.py` ~lines 345-371) picks ONE host receiver for a beacon = the receiver with the most rows over the whole season, builds epochs from the host's detections, and gives `transNo` only to rows within +/-0.5 pulse period (30 s) of a host epoch. Rows with no host epoch get NaN and are dropped before `filter_deep_beacon` (as legacy step 5 does before Deng).
- Cause for 7D2D: host ZOI07 stops hearing 7D2D after 2025-09-08 07:25 (clock-fixed). From 09-08 to 09-17 every other receiver's 7D2D detections have no host epoch: NaN per day 15,961 / 23,576 / 21,285 / 19,798 / 21,137 / 21,317 / 15,528 / 13,047 / 2,141 / 1,053. Those days account for about 145k of the 162,562 dropped rows. Before 09-08 the daily NaN count is 2-80. ZOI08, ZOI10, CFD08 etc. keep hearing the beacon through 09-15/17 (about 2,500/day), so the data exist and are lost only by the host rule.
- 7DBC: host CFD04 stops about 09-14 (418 rows that day, then 0); smaller loss, 33,719 rows, about 2.4% per receiver. FFC7: host ZOI08 runs to 09-17; loss 1,811 (0.1%), baseline edge-of-window effect.
- No code or data changed. Proposed fix, not applied (needs project-lead decision, it touches legacy epoch logic): choose the host per day (or fall back to the next best-covered receiver once the host has no detection within a pulse period), then rerun first-arrival and second stage for 7D2D and 7DBC. Alternative: accept the loss and restrict beacon use to before the host's last detection.
- Same rule also affects 2019 in principle; 2019 FF76/FF74/FF78 dropped 968/688/597 rows, small, no action.
